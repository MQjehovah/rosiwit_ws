## 0. 结论先行

实车行驶（318 s）回放分析的根因：**跟踪线程一帧的活太多**（平均 126 ms，预算 100 ms），核心队列常满，21% 的帧被丢，
而且这些丢弃在日志里看不见。本次只做两件事（范围是和用户确认过的）：

1. **账本（地图维护器）的写入挪出跟踪线程**，成为独立的地图更新线程 —— 定位只投递观测，读账本只走不加锁的视图。
2. **跟踪线程的实时优先级真正生效**（systemd drop-in `LimitRTPRIO=40`），并去掉"首帧后把 OpenMP 工作线程降回普通调度"。

190 s 实车录包回放（同一台机器、同样的整机负载），与改动前对比：

- 跟踪质量没变（成对 fitness、横向偏差都在基线间噪声内）；RT 那一组按日志时刻配对时纵向领先 0.19 m（中位），
  横向不变 —— 这是**输出更新鲜**（改动前的位姿带着队列等待，更滞后），不是轨迹岔开。
- 求解本身也快了（p50 48 → 35 ms）：主线程和工作线程都是实时调度后，栅栏处不再等一个被抢占的非实时线程。
- **积压是减轻了，没有消除**：RT 之后仍有约 5% 的帧被丢。长尾帧的耗时在求解器自己身上 —— 那些窗口迭代
  p50/max = 7/12 轮（正常 4–5 轮），单帧求解 100–160 ms，连续几帧超过 100 ms 的帧周期就把容量 2 的队列顶满。
  这属于求解器收敛判据（已单列为后续项），不在本次范围。

## 1. 线程模型（定位模式）

| 线程（comm） | 干什么 | 调度 |
|---|---|---|
| `slam_loc`（跟踪线程） | 预测 / 去畸变 / 配准 / 融合 / 状态机 / 发布；**判定**是否写图并投递 | 代码会自己设 `SCHED_FIFO 40`（需要单元 `LimitRTPRIO>=40`）；**当前未启用 = 普通调度** |
| `slam_loc`（它的 OpenMP 工作线程） | 求解器的并行那一半（num_threads=2） | 跟随创建者（RT 启用时 = SCHED_FIFO 40，否则普通调度） |
| `slam_mapupd`（**新**，地图更新线程） | 账本的全部读写：逐帧 `onLocalized`、段级 `mergeChunk`、lifelong 刷新、工作图落盘的分片标注 | 普通调度 + nice 10（线程入口显式降级，不依赖创建者） |
| 建目标线程 | 裁剪工作图 + 建新匹配器 | 普通 + nice 10 |
| 落盘线程 | 降采样 / 压缩 / 写盘（不碰账本） | 普通 + nice 10 |
| 重定位建库 / 全局搜索 / 一致性 | 各自线程 | 普通 |

职责边界：**定位只负责产出位姿和可信度；地图更新是另一个组件。** 两者之间只有一个队列。

## 2. 地图更新线程（`maintainer/map_update_worker.h`）

```
跟踪线程                               地图更新线程 (slam_mapupd)
──────────────────────────────         ──────────────────────────────────────────────
写图门槛 (base_anchored / pose_stable /
         coast / allowMapInsert /        Localized  → onLocalized(pose, scan, match, true)
         anchorOk)  —— 判定不变          Merge       → mergeChunk(kf.pose, kf.world)
        │ submit() 永不阻塞      ──▶      Lifelong    → overlay 快照 + 刷新重定位器
        ▼                                 (队列空的间隙) 工作图落盘分片标注 advanceSaveAnnotation
读账本只走不加锁的视图:
  revision() / lastNovel*  原子量
  filterDeadBase()         判死体素集的写时复制快照
  cachedPersistencyCoverage()  每次写入后算好的缓存
```

- **观测任务**（`Localized`）有界（容量 3）：满了丢**最旧的观测**。账本证据是累积的，丢几帧只是少几票；
  反过来让定位等账本才是错的。
- **结算任务**（`Merge` / `Lifelong`）不丢：它们是整段证据的一次性结算，丢了就没了；生产方本身限速
  （每 25 帧 / 每 `refresh_frames` 帧）。
- 队列按提交顺序执行；任务抛异常被捕获并计数（`mapupd_fail`），不杀线程。
- `flush()`：丢掉排队的、等手里那个做完 —— 换图（`setMapImpl` / `setMapData`）和析构前调用。
  换图期间的 `abortMapSaveAndWait()` 先置作废标志、再 flush 地图更新线程、最后等落盘线程；
  flush 时**不能**持 `m_save_mu`（分片标注交接要拿它）。
- 账本主锁（`OverlayMapMaintainer::m_mu`）现在只在地图更新线程、IO 发布线程、换图线程之间竞争；
  持锁的一次写入实测 30–550 ms，跟踪线程每帧都要读账本，等这把锁 = 账本开销原样回到帧预算里。

回放里地图更新线程自己：任务耗时 ema ≤ 91 ms、单次最大 334 ms，丢弃观测 0，失败 0（190 s）。

## 3. 实时优先级（设计记录——**当前未启用**，见文首状态更新）

- 节点代码一直在 `localizationWorker` 里设 `SCHED_FIFO 40`，但单元 `LimitRTPRIO=0`，`pthread_setschedparam`
  一直返回 EPERM 且**静默**。现在以读回的调度策略为准打一行日志（见部署手册 §4.1 / §5）。
- 去掉"首帧后把除跟踪线程外的所有线程降回普通调度"：它把求解器的 OpenMP 工作线程也降了，
  实时主线程就在栅栏处等一个非实时线程。工作线程空闲时不会霸占 CPU（libgomp 默认有限自旋后睡眠；
  实测它 37% 的 CPU 就是并行那一半的活，不是自旋）。
- 内核 `sched_rt_runtime_us=950000` 没动：跟踪线程把一个核占满超过 950 ms/s 时会被内核按住到下一秒
  （回放里偶发的 44–51 ms"没在运行"就是这个）。它只在已经过载的那些秒里出现，本文件不改它。
- 试过 `OMP_WAIT_POLICY=passive`：工作线程 CPU 没降（37.9% → 36.5%），主动切换多 10 倍，丢帧 95 → 124。**不采用。**
- **回放时不要用优先级 50**：内核中断线程是 50，同级时中断线程抢不到 CPU。当天用 50 的回放期间 USB 主机控制器都报了
  `xhci-hcd ... unknown event type 37`（不带 RT 的回放没有），当晚一次之后整机硬重启。本文的回放数据是在撤回之前、用 50 测的。

## 4. 可见性（新日志字段）

- `[LocPerf] ... queue=N age_ms_ema=A drop_total=T drop_50=D`：帧龄 = 这帧在核心队列里等了多久；
  `drop_*` 是**跟踪线程队列**（`m_loc_buf`）的丢弃数。之前这里的丢弃在日志里看不见
  （`[slam_algo] input 1s` 报的是 ROS 层通道，不是这个队列）。
- `[quality] ... mapupd_ms= mapupd_ema= mapupd_max= mapupd_drop= mapupd_fail= mapupd_q=`：地图更新线程。
- `[FramePerf]` 的 `ledger` 子阶段现在量的是"门槛判定 + 投递"（≈0）。
- `tools/drive_report.py` 解析以上字段；`tools/replay/mu_report.py`（回放汇总）、`tools/replay/traj_cmp.py`
  （轨迹差分解成纵向 / 横向）是本次用到的分析脚本。

## 6. 需要知道的副作用与发现

1. **账本现在收到完整的帧。** 改动前跟踪线程丢帧时，账本也跟着少写（回放：600 vs 700 个写入帧 / 190 s）。
   账本算法没动，变的是输入完整了。回放里观察到：起始区域判死的底图体素 386 / 369 / 359（新，3 次）对
   291 / 299（改动前，2 次）。这些体素不在配准目标的裁剪范围内（建目标时 `removed` 仍为 0–1），所以对定位没影响。
   **也就是说：此前在实车上看到的判死 / 沉淀速度，是在丢帧 10–20% 的条件下观察到的；阈值（`base_voxel_w`、
   `persist_hits` 等）是按那个条件调的。** 部署后需要在实车行驶中重新看一遍 `dead_base` 的增长是否合理。
2. **`novel_commits` 不是"地图长了多少"的度量。** 它计的是候选达到票数的次数，包含没有改变地图的重复提交
   （回放里它每帧几十地涨，而触发建目标的账本版本号一动不动）。地图是否真的变了看 `revision`（建目标次数）。
3. 用合成场景验证过：新结构候选的计票**不受跟踪线程丢帧影响**（账本只数自己写入的帧；同一串观测，
   稀疏写入只是把沉淀推后，票数和沉淀数一样）。第 1 条里判死变多的机制是"每个视角要有采到那条射线的帧"，
   这是推断，没有单独做实验证实。
