# 全局重定位 2026-11-26：修了什么、卡在哪、下一步

> 目标：判丢/冷启动后能**又快又准**地全局重锁。
> 现状：**基础设施已补齐并验证；scan_context 的召回精度在这张图上还差一步，
> 所以默认仍是 `relocalizer: none`（行为与之前完全一致）。**

## 1. 以前的真实状态（3 个坑）

1. **`relocalizer: none` 时全局重定位是死代码。**
   `runGlobalRelocOnce()` 一进来就 `if (... || m_relocalizer_name == "none") { 清请求; return; }`，
   判丢后唯一的恢复路径是 `tryBoundedRecovery()`：27 个起点（±1.5 m / ±10°）× 每次最多 3 s
   的局部 GICP 穷举。它只能在"位姿大致还对"时救回来；真丢了就是每帧烧 3 s，
   帧率从 10 Hz 掉到 1.4 Hz，且永远回不来。
2. **ScanContext 的库根本没人建。** `ScanContextGlobalLocalizer::setMap()` 只会去读
   `<map>.scdb`，而这个文件只有建图侧（loop closure）才会写；现场没有 → `setMap` 直接
   `return false` → `ensureRelocalizerMap()` 永远 false。等于"选了 scan_context 也不工作"。
3. **查询点云的坐标系不对。** 全局重定位把原始雷达系扫描直接算描述子；而地图关键帧是
   车体系（俯装 41.67°）。同一地点两边的描述子能差到 20+ m。

## 2. 本轮改动（与具体算法无关的部分，已验证）

| 改动 | 效果（实测） |
|------|--------------|
| `setMapWithKeyframes()`：切图后用地图关键帧**后台自动建描述子库** | 1607 关键帧 **261 ms**，写 `<map>.reloc.scdb` 缓存 |
| 建库后台化 + 就绪判断 | 整库（258 万点降采样 + KD 树）**2.0~2.7 s** 完成，`ok=1`，回调不阻塞 |
| 查询云走 `toBodyFrame()`（雷达→车体系） | 与关键帧同口径 |
| 描述子高度截断 `sc_z_cap`（默认 4 m）+ 可选水平系旋转 `sc_level_r` | 两边 max 高度从 34.2 m vs 7.15 m → **4.0 vs 4.0**（可比） |
| 召回兜底：阈值全灭时按 ringkey 取前 K，交给覆盖率/精配/歧义裁决 | 不再"一次不命中就永久静默失败" |
| 精配提前停：拿到两个"够好且分得开"的候选就不再跑 | 最坏精配次数 N → 2~3 |
| 失败可见：`no candidate` / `refine weak` / `[SCProbe]` 日志 | 现场能分清是召回失败还是精配淘汰 |

`relocalizer: none` 时以上全部不生效，行为不变。

## 3. 卡在哪（实测数字）

用录包 + 故意偏 2.5 m 的初始位姿（旧代码必然永久 LOST）做端到端测试：

```
[SCProbe] db=1607 scan_pts=11697 rk_best=0.40 hits=8 best_d=0.81 thr=0.40 fallback=1 qmax=3.0 kmax=3.0
global refine weak: best=0.347 second=-1 -> retry
```

- 同一地点的描述子距离 **0.75~0.81**，阈值 0.4 → 只能靠兜底候选；
- 兜底候选精配分只有 **0.29~0.35**（注入线 0.85）→ 不能注入。

也就是说：**召回出来的不是那个地方**。已经排除的因素：量纲（qmax/kmax 已一致）、
雷达系（已转车体系）、搜索半径（80→40→15 m 都试过，反而更差）、精配代价（已提前停）。

剩下的最可能原因：描述子库是用**地图关键帧原始点云**建的，而查询是**当前单帧扫描**，
两者在遮挡/密度/视野上系统性不同（关键帧是累积图、被 voxel/高度带裁剪过）。
`tools/reloc_bench.cpp` 里建库用的是**"按关键帧位姿从全局图切视野"**（`cutScan`），
那才是和查询同口径的做法。

## 4. 下一步（按性价比）

1. **描述子库改成"按关键帧位姿从全局图切视野"**（与 `reloc_bench` 一致）。
   1607 个位姿太多，按空间均匀降到 ~400~600 个（10~15 m 一个地方），
   后台建库约 10~30 s（ARM 上 30~90 s），可缓存。做完 `[SCProbe] best_d` 应 < 0.4。
2. 若不想动库：**临时把现场切到 `fpfh_ransac`**（3D 特征，历史实测 0.99+），
   代价是判丢后单次重试 ~6 s + 3 s/候选，恢复要几十秒 —— 但"能回来"。
3. 长期：把 `retry_interval` 与"重定位预算"绑定，判丢后先快后慢地重试
   （SC 快就多试，FPFH 慢就少试）。

## 6. 召回调参实测（同一帧、同一张图）

`[SCProbe] best_d` 越小越好（阈值 0.40）；`qmax/kmax` 是两边描述子最大值（同口径自检）。

| 库的建法 | 查询预处理 | best_d | 结论 |
|----------|-----------|--------|------|
| 关键帧原始点云 | 原始扫描 | 0.75~0.81 | 不可用 |
| 关键帧原始点云 | + 水平系旋转 | 0.75 | 不可用 |
| 关键帧原始点云 | + 水平系 + 0.3m 降采样 | 0.74 | 不可用 |
| **全局图切视野**(1m 抽稀) | + 水平系 + 降采样 | 0.46~0.50 | 接近，但召回候选仍过不了粗筛 |
| **全局图切视野**(5m 抽稀, 365 地点) | + 水平系 | **0.388 < 0.40** | **召回成功**（当时粗筛门限太严 0.8m/0.30 → 被淘汰） |
| 全局图切视野 + 半径 15m | — | 0.81~0.97 | 更差（近场密度差异被放大） |
| 切视野 + **掩码距离**（只比共同非空格，z_cap=4） | + 水平系 + 降采样 | **0.06~0.13**，但 365 地点里 **78 个**都 <0.4 | 指标退化了（z 饱和到 4，大家都"像"） |
| 同上，z_cap 抬到 8（不饱和） | — | 1.28~1.40 | 反而过大（地图切片的 max-z 与单帧扫描差 1m+） |

结论：**"每格最大高度"这个描述子在地图切片 vs 单帧扫描之间没有可用区间**——
截断到 4 m 就全部饱和（78/365 都命中），不截断就差 1.3 m。这不是调参能解决的，
是"两类点云不同源"的本质问题。

## 7. 覆盖率打分模式（已实现，实测仍不够）

为了彻底绕开描述子口径问题，实现了 `sc_use_coverage_score`：不用描述子，直接把查询扫描
放到每个地点上量覆盖率，再对 top 地点做 (dyaw ±4°) × (dxy ±1 m) 细搜，最后交给管线 GICP。

实测（同一帧）：

```
[SCProbe] mode=coverage places=365 best_cov=0.91~0.94 yaw=-15 dxy=0.0
global refine weak: best=0.11~0.19 second=0.10~0.16 -> retry
```

关键发现：**1.2 m 容差下的"覆盖率"不具区分度** —— 仓库里几乎任何位姿都有 0.9，
因为到处都有墙/货架。0.91 并不代表"找对了地方"。而管线精配用的覆盖率是 **0.3 m
容差**（`matcher.inlier_dist`），这个才具区分度：正确位姿 0.85~0.9，错误位姿 0.1~0.2。
精配给出的 0.11~0.19 说明候选**确实是错的地方**。

所以下一步必须让"召回打分"用 **0.3 m 容差**（而不是 1.2 m），并且必须解决朝向：
查询时刻的车头方向与建库地点的朝向无关（同一地点可以任意朝向经过），
±30° 的假设不够 —— 要么全 360° 扫（代价高），要么用描述子/ring-key 给朝向。

**结论**：全局重定位的召回质量是"研究性问题"，必须用**离线批量评测**来迭代
（`tools/reloc_bench.cpp` 已有骨架：给定地图+轨迹，对每个位姿做 recall@K / 位姿误差），
再用单帧跑包（每次 9 分钟）验证。继续用单帧日志盲调性价比极低。

## 8. 建议（按顺序）

1. **现场先用 `fpfh_ransac`**（配置一行）：3D 特征，不受俯装/朝向假设影响，历史实测 0.99+；
   代价是判丢后单次 ~6 s + 3 s/候选，恢复要几十秒 —— 但"能回来"。
2. 用 `tools/reloc_bench` 建离线召回评测（地图+轨迹 → recall@K），把"召回"和"精配门控"
   分开迭代；召回目标：正确地点进 top-10，且 0.3 m 容差覆盖率 ≥ 0.3。
3. 召回方案二选一：① 全 360° 朝向扫描 + 0.3 m 容差覆盖率（精确但慢，适合后台）；
   ② 保留 ScanContext 但**只用 ring-key 做朝向+粗筛**，打分换 0.3 m 覆盖率。

结论与下一步：
1. **库必须用"全局图切视野"**，且位姿抽稀到 ~5 m（太密会互相混淆）；本仓库代码已按此实现（`sc_db_from_map: true`）。
2. 粗筛门限已放宽到 **1.2 m 容差 / 0.25 覆盖**，并把全局精配 `icp_max_corr_dist` 提到 4 m，
   这样"候选离真值 1~5 m"仍能进 GICP 收敛 —— 这一步还没在整轮回归里验证。
3. 若 `best_d` 仍在 0.4~0.5，建议把描述子换成**带占位掩码的余弦距离**（对空单元不罚分），
   或改成"关键帧点位 + 描述子 top-K 后用覆盖率直接重排"，而不是只看 max-z 的 L1。
